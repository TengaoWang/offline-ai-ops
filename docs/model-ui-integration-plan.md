## 1. 已确认的范围

本计划不再只是“模型 + RAG + 主聊天 UI”子计划，而是需求文档 P0 的完整交付计划。

### 1.1 P0 必须交付

| 需求 | 本计划的实际交付 |
| --- | --- |
| FR-1 断网排障闭环 | 选择技能或描述故障 → 白名单采集 → 规则树 + AI 判定 → 带出处报告，全程不访问外网 |
| FR-2 技能库 | 预置网络连通、磁盘存储、服务进程、日志审计 4 个完整技能包；新增合法目录可自动识别 |
| FR-3 一键采集 | 读取 `collect.yaml`，按序执行只读命令，逐条返回命令、原始输出、状态和耗时 |
| FR-4 规则树 | 安全解析 `rules.yaml`，输出命中规则、中间结论、根因分支和可展开判定路径 |
| FR-5 混合判定 | 确定性阈值由规则树处理；只有规则未覆盖的复杂问题才交给本地 AI，并显式标注判定来源 |
| FR-6 故障报告 | 生成严重/警告/正常分级报告，每项包含现象、根因、建议修复指令、判定来源和手册依据；修复指令只展示，不执行 |
| FR-7 强制溯源 | 问答和报告中发布的每条结论都映射到手册文件、章节、PDF 页序和原文；无依据时拒答或列入未决项 |
| FR-8 沉淀技能 | 从已完成排查生成新技能包，安全校验后原子写入 `skills/<name>/`，刷新后可再次执行 |
| FR-9 白名单执行器 | 默认拒绝，只允许已声明的只读命令和参数；禁止 shell 拼接，拦截 `;`、`&&`、`\|`、反引号等注入 |
| FR-10 U 盘即插即用 | 交付 Windows 10+ / macOS 12+ 便携启动方案，同时提供 Ollama 和 llama.cpp 后端包，不在目标机下载依赖 |
| FR-11 手动 vs AI 对比 | 对同一场景记录真实手动和 AI 耗时、步骤、翻手册次数、采集命令数，生成可导出对比表 |

### 1.2 执行目标与模拟边界

- 真实执行器首先支持受控本机/测试目标的只读命令，使用 `shell=False` 的参数数组调用。
- P00 交换机测试模拟器作为无真实设备时的可重复验收目标，但请求、采集过程、报告和 Evidence 必须持续显示 `simulation`。
- FR-1 不能只靠 `DEMO_RUNS` 通过；至少一条端到端场景必须经过真实白名单执行器。
- 主聊天支持两类明确意图：手册问答调用 RAG；故障描述或明确技能调用真实诊断引擎。前端不能用固定回放伪装真实执行。

### 1.3 本次不实现

- P1 需求 FR-12～FR-14，除非它们是 P0 安全性和可验收性的必要基础。
- 开放式 Agent 任意工具调用。
- 自动执行修复指令或任何设备/操作系统配置性写操作。
- 企业级多租户、远程凭据管理、大规模设备群管理和通用任务队列。
- 通用知识库版本管理 UI、历史版本浏览和任意回滚；知识库快照只用于原子发布和失败保护。

## 3. 目标架构与实施原则

### 3.1 真实诊断主线

```text
选择技能 / 描述故障
          │
          ▼
  技能路由与目标校验
          │
          ▼
  collect.yaml → 白名单校验 → 只读执行器
          │                         │
          │                         └─ 逐条原始输出/失败/耗时
          ▼
  结构化采集结果 → rules.yaml 规则树
          │                         │
          │                         └─ 命中路径/确定性结论
          ▼
  规则未覆盖项 → 本地 AI + 当轮 RAG 依据
          │
          ▼
  核验器 → 分级报告 + 出处 + 未决项
          │
          ├─ 主聊天/UI 展示
          ├─ Evidence 实测记录
          └─ 用户确认后沉淀为技能
```

### 3.2 模块边界

| 模块 | 权威职责 |
| --- | --- |
| `engine/skill_loader.py` | 扫描和校验技能包，非法包不可执行 |
| `engine/executor.py` | 白名单、参数校验、无 shell 执行、超时、输出限制和逐条事件 |
| `engine/rules.py` | 安全解析规则条件并输出可追溯路径；禁止 Python `eval` |
| `engine/skill_engine.py` | 编排采集、规则、AI 补充、RAG、报告和技能沉淀 |
| `llm/` | 问题分流、本地生成、RAG、出处核验和健康状态 |
| `ui/service.py` | HTTP 输入校验、错误映射、运行互斥和稳定 JSON/SSE 契约 |
| `ui/` | 只渲染后端事实；不生成规则结论、出处或伪执行状态 |

### 3.3 安全和诚实降级

- 白名单默认拒绝；技能包不能通过添加文件自动扩大全局白名单。
- 命令使用参数数组调用，不经过 shell；只保留必要环境变量，使用受控工作目录。
- 修复命令仅作为文本建议返回，不进入执行器。
- 规则结论使用 `refs.yaml` 绑定出处；AI 结论只能引用本轮 RAG 片段编号。
- 没有依据的根因或修复建议不得作为已确认报告项发布，只能进入 `unresolved`。
- `real`、`simulation`、`mock` 必须作为每次运行/回答的固有字段持久化，不能从当前健康状态反推。
- 模型/索引/执行器异常返回系统错误，不得转成“手册中未找到依据”或成功报告。

## 4. 核心契约

### 4.1 技能包契约

每个技能目录必须包含：

- `SKILL.md`：名称、适用范围、目标类型、安全边界和人工处置提示。
- `collect.yaml`：稳定命令 ID、参数模板、超时、输出解析器和是否必需。
- `rules.yaml`：规则 ID、受限条件表达式、结论、下一分支、根因和严重级别。
- `refs.yaml`：规则/根因到真实索引出处的映射，不接受仅有展示文字的伪出处。

加载器必须完成 Schema 校验、目录包含检查、重复 ID 检查、命令白名单检查和出处可解析检查。无效技能可在 UI 中显示错误，但不可执行。

### 4.2 `SkillEngine` 稳定结果

```json
{
  "run_id": "r-...",
  "skill": "disk-full",
  "execution_mode": "real",
  "target": {"kind": "local", "display_name": "test-host"},
  "collected": [
    {"command_id": "disk-usage", "display": "df -h", "output": "...", "status": "success", "duration_s": 0.3}
  ],
  "rule_path": [
    {"rule_id": "r1", "matched": true, "branch": "disk-warning"}
  ],
  "findings": [
    {
      "severity": "warning",
      "title": "...",
      "symptom": "...",
      "root_cause": "...",
      "fix_commands": ["..."],
      "judged_by": "rule",
      "sources": [{"file": "manual.pdf", "section": "...", "page": 112, "text": "..."}]
    }
  ],
  "unresolved": [],
  "timing": {"collect_s": 4.1, "analysis_s": 8.2, "total_s": 12.3}
}
```

`execution_mode` 只允许 `real` / `simulation` / `mock`。`findings` 中的发布结论必须有真实 `sources`；否则转入 `unresolved`。

### 4.3 HTTP / SSE 契约

| 方法 | 路径 | 职责 |
| --- | --- | --- |
| GET | `/api/skills` | 列出可执行和无效技能及校验状态 |
| POST | `/api/diagnose/runs` | 提交技能/故障描述、目标和执行模式，返回 `run_id` |
| GET | `/api/diagnose/runs/{run_id}/events` | SSE 逐条返回 `start/collect/rules/ai/report/done/error` |
| GET | `/api/diagnose/runs/{run_id}` | 返回已完成运行或明确的未完成状态 |
| POST | `/api/skills/save` | 将已完成运行生成、校验并原子发布为技能 |
| POST | `/api/ask` | 本地手册多轮问答 |
| GET | `/api/health` | 模型、索引、执行器、技能库、运行互斥和发布版本状态 |
| POST | `/api/manuals/upload` | 校验并暂存手册 |
| POST | `/api/manuals/ingest` | 在候选快照中建索引，校验后切换 |

诊断、手册建库和模型生成必须有明确资源策略。P0 允许同一进程内的有界互斥，但不允许隐式排队、自动重试或重复执行。

### 4.4 手册问答契约

`POST /api/ask` 保留 `question`、成对的已完成 `history`、`conversation_id` 和 `request_id`。成功响应至少包含：

- `answer_type`: `generated` / `extracted` / `not_found` / `clarify` / `intro` / `out_of_scope`
- `execution_mode`: `real` / `mock`
- `verification_status`: 当前只允许精确的 `citation_and_command_checked`、`source_extract` 或 `not_run`
- `citations`: 文件、章节、PDF 页序、原文和显示标签
- `index_revision`、`retrieval_mode`、`latency_s`、`request_id`、`conversation_id`

后端必须区分：检索无依据为 200 `not_found`；业务核对失败为 200 `extracted`；协议错误为 502；未就绪/模型不可用为 503；超时为 504。系统异常不得被静默转成 `extracted` 或 `not_found`。

## 6. 实施阶段

### M0：P0 契约、候选改动和安全边界冻结

1. 建立 FR-1～FR-11 到模块、接口、测试和交付物的双向追踪表。
2. 对所有未提交文件/行为变更完成保留、调整、移除或暂缓决定。
3. 冻结技能包 Schema、`SkillRunResult`、事件流、错误码、执行模式和出处核验语义。
4. 冻结白名单、参数、环境变量、工作目录、超时、输出上限和修复命令不执行边界。
5. 冻结 Ollama/llama.cpp 共用的模型适配接口和发布模型候选，不在没有质量重验的情况下换模型。
6. 修正系统异常被静默转成 `extracted` / `not_found` 的契约问题。
7. 运行当前测试并记录基线。

出口条件：

- FR-1～FR-11 全部有负责模块、实施阶段和至少一条可执行验收用例。
- 没有未声明的功能回退、范围扩张或伪演示路径。
- 执行器和模型/RAG 的信任边界可用合同测试表达。

### M1：真实技能引擎、白名单和种子技能包

工作：

1. 实现 `engine/skill_loader.py`、`executor.py`、`rules.py`、`skill_engine.py` 和共享 Schema。
2. 实现 `local`、`simulation` 目标适配器；真实执行器禁止 shell，默认拒绝所有未白名单命令。
3. 实现受限规则表达式和可追溯路径，不使用 `eval`。
4. 建立 4 个完整种子技能包，命令、规则和出处均通过 Schema 校验。
5. 实现逐条运行事件、输出上限、取消后状态和部分失败的诚实报告。

出口条件：FR-2、FR-3、FR-4、FR-9 的自动化测试通过，且至少一个技能使用真实执行器完成采集和规则判定。

### M2：混合判定、强制溯源和真实报告

工作：

1. 将规则未覆盖的结构化采集结果交给本地 AI，不让模型生成或选择要执行的命令。
2. AI 补充判定每轮重新检索，只允许引用本轮片段编号，并复用命令/出处核验。
3. 合并规则结论和 AI 结论，生成分级报告；无出处内容只进入未决项。
4. 完成手册上传、候选建库、校验切换和失败保护。
5. 修正问答错误语义、执行模式和核验状态。

出口条件：FR-5、FR-6、FR-7 质量门禁通过；报告与问答不发布无依据结论。

### M3：主聊天真实闭环、技能沉淀和 Evidence

工作：

1. 主聊天明确支持手册问答和故障诊断；一键体检只运行用户已选技能。
2. 将 SSE 采集、规则路径、AI 标识、报告、出处和未决项与真实 `SkillRunResult` 绑定。
3. 模拟通道持续显示标识；普通诊断失败不自动转模拟。
4. 存为技能时只使用已执行命令、已验证规则和真实出处，校验成功后原子发布。
5. Evidence 自动读取真实运行数据，人工数据明确标注为现场记录；需求基线不伪装成实测。

出口条件：FR-1、FR-8、FR-11 的浏览器端到端验收通过，且不存在固定数据伪装真实执行。

### M4：Ollama / llama.cpp 双后端与 U 盘便携发布

工作：

1. 实现不依赖 UI 分支的统一本地模型适配层，Ollama 和 llama.cpp 输出映射到同一错误/响应契约。
2. 准备 Windows 10+ / macOS 12+ 的 Ollama 包和 llama.cpp 包，包含锁定版本、模型、索引、静态资源、启动脚本、许可说明和 SHA-256 清单。
3. 启动器只绑定 `127.0.0.1`，检查端口、运行时、模型和索引，就绪后打开系统默认浏览器。
4. 启动期间不下载、不自动安装全局依赖，错误要给出可操作提示和日志路径。
5. 若 8GB CPU-only 目标需要换用较小量化模型，必须对 FR-5/FR-7 题集和 30 秒性能门禁重新验收。

出口条件：FR-10 在干净 Windows/macOS 目标机按第 7 节通过，发布包全程无下载。

### M5：P0 端到端验收与文档收尾

1. 运行全部单元、合同、安全、真实模型、浏览器和便携包测试。
2. 按 FR-1～FR-11 追踪表收集证据，每项记录环境、步骤、预期、实际结果和产物路径。
3. 任何未通过项保留在报告中，不从统计中删除，不将 P00 模拟结果替代真实执行结果。
4. 更新启动、目标选择、技能包编写、安全边界、手册入库、错误恢复和发布说明。

## 7. P0 验收标准

### 7.1 FR-1～FR-11 逐项门禁

| 需求 | 通过条件 | 必须保留的证据 |
| --- | --- | --- |
| FR-1 | 拔网线、关 Wi-Fi 并阻断外网后，场景 A/B 均从技能/故障描述走到完整报告；至少一个场景使用 `real` 执行器 | 录屏/截图、运行 JSON、进程出站连接记录 |
| FR-2 | 4 个种子技能包均含四个规定文件、通过 Schema 并可执行；复制一个新合法目录后无需改代码即出现 | 技能校验报告、UI 截图、自动发现测试 |
| FR-3 | 一键体检按序执行技能命令，逐条显示原始输出、状态和耗时；一组验收采集在 30 秒内完成 | 事件流日志、UI 截图、计时结果 |
| FR-4 | 网络和磁盘至少 2 棵真实规则树完整运行，UI 展示命中规则和分支；恶意表达式不能执行代码 | 规则固件、路径 JSON、安全测试 |
| FR-5 | 场景 A 主结论由规则给出；至少 1 个规则未覆盖场景由本地 AI 补充，并标记 `judged_by=ai` 和真实出处 | 规则/AI 对照运行结果、模型输入输出摘要 |
| FR-6 | 验收报告至少 3 条分级项，每项包含现象、根因、修复指令、判定来源和出处；修复指令没有被执行 | 报告 JSON/导出文件、执行日志 |
| FR-7 | 人工逐结论抽查至少 5 条，文件、章节、PDF 页序、原文及结论语义均一致；所有发布结论 100% 有依据，无依据项拒答或进入未决项 | 抽查表、原手册页截图、无答案题集结果 |
| FR-8 | 完成一次排查后点“存为技能”，生成四个文件，校验后出现在列表并能再次执行；同名和非法名称不覆盖旧包 | 新技能目录、校验报告、第二次运行结果 |
| FR-9 | 允许的只读命令可执行；`rm`、`reboot`、`write memory` 和包含 `;`、`&&`、`\|`、反引号、换行注入的输入全部被拒绝；不经过 shell | 单元/集成安全测试、拒绝事件日志 |
| FR-10 | Windows 10+ 和 macOS 12+ 干净机器上，Ollama 包和 llama.cpp 包均在无网情况下双击启动，3 分钟内浏览器打开且健康检查就绪；不写入全局依赖 | 4 组启动记录、版本/授权/SHA-256 清单、无网证据 |
| FR-11 | 对同一场景产出手动与 AI 实测对比，含耗时、步骤、翻手册次数、点击数和命令数；需求中 25 分钟/14 步/3 次与 3 分钟/1 次/6 条必须标记为需求基线或真实实测，不得混淆 | 现场原始记录、导出的 Markdown/CSV 对比表 |

### 7.2 RAG 与报告质量门禁

使用未参与提示词调试的独立题集：

- 至少 10 道手册可回答题，有效、与原文一致的回答至少 9/10。
- 至少 12 道无答案题，分别覆盖明显越界、交换机领域但手册未覆盖、条件不足和相近概念误检索；100% 不得发布实质性无依据结论。
- 至少 5 组多轮问答，每轮重新检索，不串会话、不直接复用上轮旧出处。
- 至少 4 组诊断场景，覆盖规则主判、AI 补充、无依据未决和部分采集失败。
- “回答有用率 ≥90%”与“所有已发布结论 100% 有依据”是两个独立门禁；允许保守拒答，不允许用 9/10 容忍一条幻觉。
- 所有失败样例保留并说明，不从统计中删除。

### 7.3 异常、性能和离线门禁

- 故障注入验证：模型不可用只返回 503，超时只返回 504，协议错误只返回 502；均不得返回 HTTP 200、`extracted`、`not_found` 或成功报告。
- 执行器中一条命令失败不得伪造输出；按技能包必需/可选标记决定继续或停止，报告明确列出未能获取项。
- 性能测试固定硬件、后端、模型、索引修订、题集和输出上限。分别记录冷启动首轮和至少 10 次热运行的采集、检索、生成、报告及总耗时。
- 需求的“单轮 ≤30 秒”按浏览器提交到完整结果可见计时；用最大值判定，不用平均值掩盖超时样例。
- 完全离线验收同时检查浏览器请求和服务进程出站连接，不能只依赖静态 HTML 扫描。
- 数据不出盒：手册、索引、日志、会话、运行结果、Evidence 和技能包均留在便携目录/本机受控目录。

## 8. 主要风险与处理

| 风险 | 处理 |
| --- | --- |
| 当前 UI 外观完整，易被误认为 P0 已完成 | 任何固定诊断数据持续显示 `simulation`；FR-1 必须有真实执行证据 |
| 技能包变成命令注入入口 | Schema + 全局白名单 + 参数校验 + `shell=False` + 恶意固件测试 |
| AI 生成要执行的命令 | AI 不得向执行器供给命令；执行列表只能来自已验证 `collect.yaml` |
| 报告有出处但结论不受支持 | 逐结论人工抽查 + 独立无答案题 + AI 只引用编号；失败时转未决项 |
| 便携包只在开发机可用 | 干净 Windows/macOS 实机、无网、非管理员、带空格/中文路径冒烟测试 |
| 8GB CPU-only 无法在 30 秒内使用 8B 模型 | 准备量化/小模型发布候选；换模型后必须重做质量和 P0 端到端验收 |
| 需求基线数字被当成实测 | Evidence 分开“需求基线”和“现场实测”，不使用预置值自证 FR-11 |
