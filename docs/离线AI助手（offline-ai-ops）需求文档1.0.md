## **1\. 背景与题目映射**



### **1\.1 真实场景还原：一次典型的"机房噩梦"**



**时间**：周五 17:40，距离下班还有 20 分钟。

**地点**：某制造企业的机房，郊区工业园区，本季度第三次光纤被施工挖断，全网断网。

**人物**：小王，入职半年的 IT 专员——平时负责装系统、修打印机，对交换机配置一知半解。此刻他是全公司唯一的"技术担当"。



**事件经过**：



1. 17:41，生产部李经理冲进来："MES 系统连不上数据库了，生产线要停了！"

2. 小王走到机柜前，面对 1 台华为 S5700 交换机和 2 台 Dell R740 服务器，心跳加速。

3\. 他第一反应是掏出手机想查报错——**没信号**（园区屏蔽 \+ 挖断光纤），微信发不出，百度打不开。

4. 他翻出一本皱巴巴的 S5700 配置手册（300 多页 PDF 打印版），对着交换机面板上一闪一闪的橙色告警灯，不知道哪一页有用。

5. 他尝试凭记忆敲命令：`ping 192.168.1.1`……不通。`display interface`？这个命令在哪台设备上敲来着？SSH 连不上交换机，console 线在哪？

6. 18:30，他满头大汗地给外包服务商打电话——对方说："今天赶不过去，你先试试重启交换机。"（错误建议，可能导致配置丢失）

7. 20:15，产线停产 2 小时 34 分钟。财务损失按产线产值折算：约 ¥47,000。小王这个周末大概率睡不好。

**这个场景里，每一个环节都是真实的：**



|痛点|真实细节|
|---|---|
|断网不是假设|偏远园区、地下机房、运营商故障，"断网 \+ 断手机信号"同时发生并不罕见|
|手册没人看得懂|S5700 手册 1500\+ 页，索引混乱，非网络专业的人根本不知道怎么查|
|经验没法复制|资深网工的排障思路（先物理层→链路层→网络层）只存在脑子里|
|AI 帮不上忙|ChatGPT/文心一言都要联网；公司数据不敢传云端；机房也不允许装软件|



### **1\.2 本项目要解决什么**

|题目要素|本项目答案|
|---|---|
|能力（Capability）<br>|资深工程师的故障诊断能力 = 设备知识（手册/工单）\+ 排障经验（先做什么后做什么）\+ 动手执行（敲命令看输出）|
|项目背景\(旧场景\)/现有场景痛点/阻碍|1. 目前AI/Agent助手使用的前提是需要有网络环境，企业级的知识问答需要大模型\(联网\)\+RAG知识库\+服务器部署\(购买其他企业的AI资源，涉及安全问题\)等，需要消耗大量人力和财力<br>2. 偏远园区、地下机房、运营商故障，"断网 \+ 断手机信号"或者必要不联网的场景同时发生并不罕见<br>3. 在离线环境下，机房排查中不同技术人员之间交流成本高、不及时<br>4. 设备手册\(如华为交换机S系列\)内容繁多复杂，索引混乱，非网络专业的人根本不知道怎么查，专业人士也需要有一定经验，但是经验没法复制，资深网工的排障思路（先物理层→链路层→网络层）只存在脑子里。|

\| 障碍（Barrier） \| **Connectivity（联网）\+ User expertise（专业能力）**：云端 AI 够不着，现场的人读不懂报错和日志 \|

\| 交付物 \| 一块外置 U盘：插到机房任何一台机器上，3 分钟启动，AI 立即上岗 \|

\| 目标用户/场景 \| 

1. 对于没有某项目的丰富运维排查经验的的现场工作人员：快速排查，生成报告，解决问题

2. 对于经验丰富的工程师：助手，提升效率

3. 对于企业公司：对应工程师到现场需要时间\(一天或者是几天\)，不懂相应设备的工作人员无从下手。可以使用离线AI助手现场快速排查问题



### **1\.3 核心差异化（为什么不是又一个离线 RAG Demo）**

定位：

1、缺少专业支持的现场人员

2、轻量、低成本（帮助现场人员完成常见问题的初步排查和适合其权限的处理，减少不必要的专家介入；需要转交时，提供完整证据，缩短专业人员的排查时间，从而降低维护成本。）

3、把经过验证的维护流程做成可复用的 Skill，自动整理和核对诊断记录，给出有依据的发现与下一步建议。

（需要AI生成一个对比表格）

**知识从哪里沉淀进来：****（目前基本来自设备官方手册，需要AI思考一下）**

**注意****：强制溯源，杜绝幻觉**。所有回答和报告都基于上传的设备手册等已有资料生成，且**必须标注参考了手册的哪一页、哪一节**。做法是：切片时保留元数据（文件名/页码/章节）→ 检索返回带编号的片段 \`\[1\]\[2\]\` → 模型只能引用这些编号 → 系统渲染成"《S5700 手册》§3\.2\.1 P47"。**没检索到出处时，模型必须回答"手册中未找到依据"，而不是硬编一个来源。**

## **3\. 技术选型\(待定\)**



### **3\.1 选型汇总**



|组件|选择|理由|
|---|---|---|

\| 推理模型 \| **Qwen3\-4B（Q4\_K\_M，约 3GB）** \| Apache 2\.0 可商用；原生 function calling / MCP 支持；中文分词效率高；thinking / non\-thinking 双模式；8GB 内存即可流畅运行 \|

\| 备选模型 \| Phi\-4\-mini 3\.8B / DeepSeek\-R1\-Distill\-Qwen\-7B \| MIT 许可备选；推理加强对比组 \|

\| Embedding \| BGE\-M3 \| 中英文混合检索强，可完全离线 \|

\| 推理引擎 \| Ollama（开发/演示）\+ llama\.cpp 单文件版（生产环境零安装兜底） \| 同一份 GGUF 跨 Win/macOS/Linux \|

\| RAG 向量库 \| Chroma（嵌入式，纯文件，随 U盘 走） \| 免部署 \|

\| 技能库引擎 \| 自研 YAML 技能包定义 \+ 批量执行器 \+ 规则树判定器 \| 固定 SOP 确定性强，可沉淀、可复用 \|

\| 判定策略 \| 规则树（确定性阈值）\+ AI（复杂根因）混合 \| 体检类判定稳、快、可解释；复杂根因交给模型 \|

\| UI \| Gradio \| 30 分钟搭完，自带流式输出 \|

\| 微调工具链（预留） \| LLaMA\-Factory（Win \+ N 卡）/ MLX\-LM（Mac） \| 下一步使用 \|



### **3\.2 关键架构决策**



1\. **用"技能库（Skill Library）"组织排障知识，而非开放 Agent 循环**：每个技能 = 采集命令（\`collect\.yaml\`）\+ 规则树（\`rules\.yaml\`）\+ 手册依据（\`refs\.yaml\`）\+ 说明（\`SKILL\.md\`）。执行器读取技能包按序批量执行只读命令，输出统一采集后交给"规则树 \+ AI"综合判定。——理由：4B 小模型的开放工具调用稳定性是最大风险；固定 SOP 确定性强、可预测、可复现，且**天然可沉淀**（技能就是文件，能 git、能拷贝、能复用）。

2\. **判定用"规则树 \+ AI"混合**：结构化的体检结论（磁盘阈值、服务状态）走规则树，确定性、可解释、可展示判定路径；非结构化的复杂根因（多输出交叉推理）交给 AI。——理由：纯 AI 判定不稳且不可解释，纯规则又覆盖不了长尾。

3\. **溯源由系统保证，不靠模型编造**：RAG 切片时保留 \`\{file, page, section\}\` 元数据；检索片段带编号；prompt 约束模型只能引用给定编号；渲染层把编号映射回真实页码。规则树的每个叶节点也绑定手册出处。——理由：小模型会编造页码，唯有"模型只引用编号 \+ 系统映射"才能保证出处真实。

4\. **沉淀 Skill 是产品能力的一部分**：一次排查后可"存为技能"，把本次的采集动作与判定规则落成新技能包文件。——理由：这是"越用越聪明"的证据，也是答辩差异化亮点。

5\. **模型产物平台无关**：GGUF 文件 \+ Chroma 向量库 \+ YAML 技能库均为纯文件，U盘 即完整运行环境。Mac 训练（若后续微调）产物转 GGUF 后在 Win 上同样可跑。

6\. **Ollama 与 llama\.cpp 双保险**：目标机房机器若允许装软件用 Ollama；不允许装软件直接运行 llama\.cpp 单可执行文件，零安装。

## **4\. 功能需求**



### **4\.1 需求清单**



#### P00

**需要一个模拟环境来测试，交换机测试模拟器**

#### **P0 必须完成（演示主线****，下方内容包含的一些命令，如\`df \-h\`、\`free \-m\`、\`ping\`/\`traceroute\`只是参考，不一定符合华为交换机这个设备****）**



|编号|需求|具体描述|验收标准|
|---|---|---|---|
|FR\-1|断网环境完成完整排障闭环<br>|用户选择技能包或描述故障，AI 自动完成"批量执行诊断命令 → 采集日志/状态/指标 → 综合判定 → 输出故障清单与解决方法"全流程，全程零网络请求|拔掉网线 \+ 关 WiFi 后，场景 A/B 全流程通过<br>|

\| FR\-2 \| **技能库（Skill Library）** \| 预置 3\~4 个技能包（网络连通 / 磁盘存储 / 服务进程 / 日志审计），每个含 \`SKILL\.md \+ collect\.yaml \+ rules\.yaml \+ refs\.yaml\`；UI 可列出、选择、执行 \| 4 个技能包均可一键执行；新增一个技能包目录即被自动识别，无需改代码 \|

\| FR\-3 \| **一键采集（日志/状态提取）** \| 单个技能包内含一组只读命令：日志提取（\`tail /var/log/\.\.\.\`）、状态提取（\`systemctl status\`、\`ss \-tlnp\`）、指标提取（\`df \-h\`、\`free \-m\`、\`ping\`/\`traceroute\`），按序批量执行并统一采集输出 \| 点【一键体检】后 30 秒内完成全部采集，UI 展示每条命令及其原始输出 \|

\| FR\-4 \| **规则树判定** \| 判定逻辑以决策树表达（YAML）：命令输出特征 → 中间结论 → 根因分支；判定路径可在 UI 展开查看 \| 预置至少 2 棵规则树（磁盘、网络）可完整走通；UI 展示"命中哪条规则、走向哪个分支" \|

\| FR\-5 \| **混合判定策略** \| 确定性阈值判定（如 \`df 使用率 \> 90%\`）由规则树处理；规则未覆盖的复杂根因交给 AI 推理，二者结论合并 \| 场景 A 主判定由规则树给出；至少 1 个长尾案例由 AI 补充判定且标注"AI 推理"来源 \|

\| FR\-6 \| **故障报告（清单 \+ 解决方法）** \| 汇总所有采集与判定结果，输出分级报告：🔴严重 / 🟡警告 / 🟢正常；每条故障给出对应解决方法与可直接执行的修复指令（写操作仅建议） \| 报告包含 ≥3 条分级项，每条含"现象 / 根因 / 修复指令" \|

\| FR\-7 \| **强制溯源（标注手册页与章节）** \| 报告与问答中的每条结论必须标注来自上传手册的文件名、章节、页码；切片保留 \`\{file, page, section\}\` 元数据，模型只引用检索片段编号，系统渲染为真实出处 \| **抽查 5 条结论，出处页码与手册实际内容一致；无依据时输出"手册中未找到依据"，不编造** \|

\| FR\-8 \| **沉淀 Skill（现场演示）** \| 一次排查完成后，点【存为技能】→ 自动生成新的 \`skills/\<name\>/\`（SKILL\.md \+ collect\.yaml \+ rules\.yaml \+ refs\.yaml 该命令参考，实际参考设备手册），下次可直接复用 \| 现场完成一次"排查→存技能→新技能出现在列表并可直接执行"的演示 \|

\| FR\-9 \| **白名单命令执行器** \| 每条命令必须过白名单校验；只放行只读诊断命令；拒绝 `rm`、`reboot`、`write memory` 等；参数注入防护（拒绝 `;`、`&&`、`\|`、反引号） \| 尝试注入 `ping 1.1.1.1; rm -rf /` 被拦截，UI 提示"该命令不在白名单，已拒绝"该命令参考，实际参考设备手册 \|

#### **🎬 场景 B：磁盘告警（辅助场景，约 1\.5 分钟）**



**剧情设定**：财务服务器弹窗"C 盘空间不足，仅剩 200MB"，管理员怕随便删文件弄坏系统，不敢动手。



**演示流程与实录**：



```Plain Text
【第 1 步】点击技能包：【磁盘存储排查】（skills/disk-full/）

【第 2 步】一键采集
  ▶ df -h                [输出] C: 237G，可用 0.2G，使用率 100%
  ▶ df -i                [输出] inode 使用率 12%（正常）
  ▶ du -sh /var/log      [输出] 89G
  ▶ ls -lhS /var/log | head -5
    [输出] 42G /var/log/syslog.1
           2.1G /var/log/kern.log.1

【第 3 步】规则树判定（disk-full/rules.yaml）
    ├─ 判定①：分区使用率 100% > 90% → 磁盘告警 ✅命中
    ├─ 判定②：inode 正常 → 排除"小文件堆积"分支 ✅
    ├─ 判定③：/var/log 占比最大 → 进入"日志目录"分支 ✅
    └─ 根因分支：日志轮转失效
       └─ 依据：refs.yaml → 《Linux 运维手册》§7.3 日志管理 P112

【第 4 步】生成报告
  📋 《故障诊断报告》
  ─────────────────────────────────────────
  🟡 警告：/var/log 分区空间耗尽
     现象：C 盘使用率 100%，inode 正常，日志目录占 89G
     根因：日志轮转失效，/var/log/syslog.1 单文件 42GB
     修复指令（建议执行）：
       1. gzip /var/log/syslog.1         # 压缩至约 4GB
       2. 在 /etc/logrotate.d/ 添加轮转策略，防止复发
       3. 或联系运维启用远程日志服务（rsyslog → 日志服务器）
     判定依据：规则树 disk-full 判定①②③
     参考来源：《Linux 运维手册》§7.3 P112

  ⚠️ 注意：直接 rm 大日志文件不会立即释放空间（进程仍持有句柄），
     正确做法是 gzip/truncate 或先重启相关服务。（此条来自手册 §7.3.2）
```

## **6\. 模块设计与接口契约**



\> **协作红线：接口契约第一天上午冻结，之后各模块用 mock 并行开发，不得互等。**



### **6\.1 核心接口**



```Python
# engine/skill_engine.py —— 全局关键契约（技能库 + 规则树 + 溯源）
class SkillEngine:
    def list_skills(self) -> list[SkillMeta]:
        """扫描 skills/ 目录，返回可用技能包（含是否内置/用户沉淀）"""

    def run_skill(self, skill_id: str, target: dict) -> SkillRunResult:
        """
        执行一个技能包（读 collect.yaml → 白名单校验 → 批量执行只读命令 → 采集输出
        → rules.yaml 规则树判定 → AI 补充复杂根因 → 生成带溯源的报告）
        返回:
        {
          "skill": "disk-full",
          "collected": [                      # 采集明细
            {"cmd": "df -h", "output": "...", "duration": 0.3, "ok": True}
          ],
          "findings": [                       # 故障清单
            {
              "severity": "warning",          # critical / warning / ok
              "title": "/var/log 分区空间耗尽",
              "root_cause": "日志轮转失效",
              "fix_commands": ["gzip /var/log/syslog.1", "..."],
              "judged_by": "rule",            # rule / ai
              "rule_path": ["判定① 命中", "判定③ 命中", "根因分支：日志轮转失效"],
              "sources": [                    # 强制溯源：手册文件名/章节/页码
                {"file": "Linux运维手册.pdf", "section": "§7.3", "page": 112}
              ]
            }
          ],
          "unresolved": ["..."],              # 无依据/未能获取的项，诚实列出
          "elapsed": 12.4
        }
        """

    def save_skill(self, run: SkillRunResult, name: str) -> str:
        """把一次排查沉淀为技能包：生成 skills/<name>/{SKILL.md,collect.yaml,rules.yaml,refs.yaml}"""
```



### **6\.2 技能包文件格式（人可读 \+ 机可执行）**




```YAML
# skills/disk-full/rules.yaml —— 判定层（规则树）
rules:
  - id: r1
    if: "df_usage_pct > 90"
    then: "磁盘告警"
    next: [r2]
  - id: r2
    if: "df_inode_pct < 80"
    then: "排除小文件堆积"
    next: [r3]
  - id: r3
    if: "du_top_dir == '/var/log'"
    then: "进入日志目录分支"
    root_cause: "日志轮转失效"    # 叶子节点 → 根因
    next: []
```



```YAML
# skills/disk-full/refs.yaml —— 溯源层
refs:
  - root_cause: "日志轮转失效"
    source: {file: "Linux运维手册.pdf", section: "§7.3", page: 112}
  - note: "直接 rm 大日志不会立即释放空间"
    source: {file: "Linux运维手册.pdf", section: "§7.3.2", page: 113}
```

## **8\. Git 协作规范**



1. 分支：`main`（永远可演示）\+ 每人 `dev-<模块>`；每天至少合入 main 一次。

2. 合 main 前：本机冒烟测试通过 \+ 主流程可跑。

3\. 大文件（gguf / 向量库 / 模型）不进 git，走 U盘 或 HuggingFace/ModelScope 私有仓库同步，命名带版本（如 \`qwen3\-4b\-ops\-v0\.2\-q4\_k\_m\.gguf\`）。**\*\*\`skills/\` 技能库必须进 git\*\***——它是纯文本、是团队的共同资产，技能迭代全程可 diff、可回溯。

4. 跨平台纪律：`.gitattributes` 统一换行符；代码用 `pathlib.Path` 不写硬编码路径；每个脚本提供 `.sh` \+ `.ps1` 双版本；Python 统一 3\.11，依赖锁进 `requirements.txt`。

5. 每天收工 15 分钟站会，议题只谈接口变化。

\| 沉淀 Skill 现场生成失败 \| 中 \| 提供"预览草稿 \+ 手动保存"两步流程；预置一个已沉淀技能兜底演示 \|
