# RAG 改进技术方案（向量检索版）

| 项目 | 内容 |
|---|---|
| 负责模块 | `llm/`（`retrieve` / `ask`） |
| 日期 | 2026-10-03 |
| 状态 | 草案，待选定方案 |
| 已定前提 | 引入向量检索；全程离线；接口不变 |

---

## 0. 现状与问题

| 环节 | 现在怎么做 | 问题 |
|---|---|---|
| 解析 | PyMuPDF 按页提取，书签生成章节路径，跳过目录页 | 页眉页脚混进正文；表格被打平 |
| 切块 | 每页按 600 字切、重叠 100 字 | 章节跨页时会被切断；块偏大，噪音多 |
| 理解问句 | jieba 分词 | 口语和手册用语对不上（"接口一直是 down"和"物理 DOWN"） |
| 召回 | SQLite FTS5 + BM25（只有关键词） | 说法不同就找不到："接口 Down"类问题的正确章节只排到第 4、第 7 |
| 排序 | BM25 分数 | FAQ、TechNotes 等内容挤占前几名；同一章节重复出现 |
| 拼接 | 5 段 × 600 字交给模型，模型返回引用编号，再由代码换成出处 | `ask` 每次要 20 到 26 秒；出处重复 |
| 评测 | 只试了 7 个问题 | 没有带标准答案的测试集，改动的效果没法量化 |

## 1. 需求和指标

需求来自《需求开发文档》FR-2、场景 A/C，以及非功能需求。

| 需求 | 指标 | 目标值（初定，测出基线后再调整） |
|---|---|---|
| 检索准确 | Hit@1、Hit@3、MRR | FR-2 的 5 道预设题 Hit@3 = 100%；整体 Hit@3 ≥ 85% |
| 听得懂口语 | 口语题的 Hit@3 | 和书面题的差距 ≤ 10 个百分点 |
| 不能装懂，没有答案时拒答 | 拒答正确率（手册里没有答案的题回答"未找到"）；误拒率 | 拒答正确率 ≥ 80%，误拒率 ≤ 10% |
| 出处可信 | 引用的页码是否在标准页码范围内 | ≥ 90% |
| 足够快 | `retrieve` 的 p95 耗时；`ask` 的 p50 耗时 | `retrieve` < 0.5 秒（Agent 每轮都可能调用）；`ask` < 12 秒 |
| 能在 8GB 机器上跑 | 峰值内存 | 4B 模型加向量模型 < 6GB |
| 能降级 | 没有向量模型时 | 自动退回只用 BM25，功能不中断 |

## 2. 三个方案都要做的部分

### 2.1 检索测试集 `eval/retrieval_cases.jsonl`

| 类型 | 数量 | 例子 |
|---|---|---|
| FR-2 的预设题 | 5 | 怎么把 GE0/0/1 配成 trunk |
| Agent 发出的查询（场景 A） | 5 | S5700 端口 VLAN 配置 排障 |
| 书面说法 | 10 | 接口物理状态 DOWN 如何排查 |
| 口语说法（和书面说法逐题对应） | 10 | 网口灯不亮，电脑连不上服务器 |
| 手册里没有答案的题 | 5 | S5700 保修多久 |

每道题的格式：

```json
{"id": "q01", "query": "...", "type": "fr2|agent|formal|colloquial|unanswerable",
 "gold_pages": [1130, 1131], "gold_section": "接口物理状态 DOWN"}
```

标准答案由 Claude 起草，**人工逐题核对页码**。

### 2.2 评测脚本 `eval/eval_retrieval.py`

- 输出 Hit@1/3/5、MRR、分题型的准确率、拒答正确率、耗时 p50/p95
- 结果保存到 `eval/results/retrieval-<tag>.json`
- 每做完一步改进就跑一次，并在第 7 节的记录表里填一行

### 2.3 解析和切块改进（向量检索的效果对切块很敏感）

- **去页眉页脚**：每页开头和结尾的那一行，如果在超过 30% 的页里重复出现，就删掉
- **按章节切块**：
  - 按书签把同一小节的文字拼起来，再切成 300 到 500 字
  - 在句号或换行处断开，相邻块重叠 1 句
  - 每块记录起始页码
- **块前加标题**：向量化时在正文前加上 `章节路径：…`，展示时不加。这样像"接口 DOWN"这种只出现在标题里的词也能被检索到

### 2.4 向量模型和存储

| 项目 | 选择 |
|---|---|
| 向量模型（默认） | `bge-m3`（Ollama，约 1.2GB，1024 维，中英文混合检索效果好） |
| 向量模型（8GB 机器备选） | `qwen3-embedding:0.6b`（Ollama，约 640MB，1024 维） |
| 调用方式 | Ollama `POST /api/embed`，一次传一批文本；仍然只用 Python 标准库 |
| 存储 | 同一个 `kb/index.db` 里新建 `vectors(id, model, dim, vec BLOB)` 表；加载时读成 numpy 矩阵 |
| 相似度计算 | 向量先归一化，查询时直接做矩阵点积。约 7 千块 × 1024 维 ≈ 30MB，单次计算是毫秒级 |
| 为什么不用 Chroma 或 Milvus | 数据量小，用不上；Chroma 默认会上报遥测数据，离线环境要额外处理；多一个依赖就多一个打包风险 |

建索引的耗时取决于机器，预计几分钟（待实测）。索引文件随 SSD 一起拷，现场不用重建。

### 2.5 接口约定（队友不用改代码）

- `retrieve(query, k=5)` 和 `ask(question, k=5)` 的参数和返回字段不变
- `retrieve` 的返回结果**只增加**两个字段：`label`（出处文字，可直接用作 Agent 的 `rag_hit.source`）和 `mode`（`hybrid` 或 `bm25`）
- `health()` 增加 `embed_model` 和 `vectors` 两项，表示向量检索是否可用
- 新增环境变量：`LLM_EMBED_MODEL`（默认 `bge-m3`，设为空则关闭向量检索）

### 2.6 速度优化（三个方案都做）

- `ask` 交给模型的片段从 5 段减到 3 段，每段上限 400 字；同一页同一章节的出处去重
- 回答长度上限设为 `num_predict=300`
- 设置 `keep_alive`，避免模型被卸载后重新加载
- Agent 在循环里直接调用 `retrieve`，不走 `ask`

## 3. 方案一：BM25 + 向量混合检索（基础版）

### 流程

```
问句 ──┬─→ BM25（jieba + FTS5）取前 20 ────────┐
       └─→ 向量检索（bge-m3）取前 20 ──────────┴─→ RRF 合并 → 同章节去重 → 前 k 段
                                                     │
                                       分数低于阈值 → 判定为没找到（不调用模型）
```

### 各环节

| 环节 | 做法 |
|---|---|
| 解析和切块 | 见 2.3 |
| 理解问句 | 不改写，原句同时送进两路检索 |
| 召回 | BM25 前 20 + 向量前 20 |
| 排序 | RRF：`score = Σ 1/(60 + rank)`，按两路各自的排名合并，不用调权重；同一章节只保留最高分的一块 |
| 拒答 | 两个条件同时满足才拒答：向量最高相似度 < 阈值 T，**并且** BM25 没有命中关键术语。T 在测试集上取值（预计 0.45 到 0.55，待实测） |
| 拼接 | 见 2.6 |
| 降级 | 没有向量模型时只走 BM25，`mode=bm25` |

### 评估

| | |
|---|---|
| 优点 | 实现最简单；命令类查询（BM25 擅长）和口语查询（向量擅长）都能兼顾；延迟增加极少 |
| 缺点 | 排序只看名次，不会细看内容；拒答阈值靠相似度，不够稳 |
| 新增资源 | 向量模型约 0.6 到 1.2GB |
| 耗时影响 | `retrieve` 增加约 0.05 到 0.2 秒（主要是给查询算向量） |
| 工作量 | 3 到 4 小时（不含测试集） |
| 风险 | 低 |

## 4. 方案二：混合检索 + 重排序

### 流程

```
问句 → [方案一：BM25 + 向量 + RRF] → 前 20 段 → 重排序模型逐对打分（问句, 片段）→ 前 3 段
                                                       │
                                     最高分 < 阈值 → 判定为没找到（不调用大模型）
```

### 各环节（和方案一不同的地方）

| 环节 | 做法 |
|---|---|
| 排序 | 用 `bge-reranker-v2-m3`（约 0.6GB）把问句和每个候选片段放在一起打分，比单纯按向量相似度更准 |
| 拒答 | 用重排序分数（0 到 1）判断，比向量相似度更稳，阈值更好定 |
| 运行方式 | Ollama 目前**不支持**重排序模型。两个选择：① 用 `llama-server --reranking` 加载 GGUF 版本（不用装 PyTorch，需先实测）；② 用 `sentence-transformers`，但要装 PyTorch，体积约 1GB 以上，打包到 SSD 很重 |
| 降级 | 重排序服务不可用时退回方案一 |

### 评估

| | |
|---|---|
| 优点 | 前 3 名的准确率和拒答判断最稳；只交给模型 3 段也不怕漏掉正确答案 |
| 缺点 | 多一个模型和一个服务进程；20 个候选逐个打分，每次检索增加约 0.3 到 1 秒（待实测）；部署和打包更复杂 |
| 新增资源 | 向量模型加重排序模型共约 1.2 到 1.8GB |
| 工作量 | 方案一加 2 到 3 小时 |
| 风险 | 中：重排序的部署方式需要先验证；8GB 机器上内存紧张 |

## 5. 方案三：混合检索 + 问句改写 + 小块检索、大块返回

### 流程

```
问句 → 大模型改写（口语 → 手册术语，输出 1 到 3 个查询）
     → 每个查询都走[方案一的混合检索]（用小块，约 200 字）→ 所有结果再用 RRF 合并
     → 返回命中小块所在的整个小节（截取约 800 字）→ 交给模型
```

### 各环节（和方案一不同的地方）

| 环节 | 做法 |
|---|---|
| 理解问句 | 用 qwen3 生成 JSON：`{"queries": ["接口物理状态 DOWN 排查", "display interface"]}`。同时用规则从问句里提取接口名、命令、告警码，原样保留 |
| 切块 | 两层：检索用小块（约 200 字，更精确）；拼接时返回小块所在小节的完整文字（上下文更完整） |
| 召回 | 每个查询各自召回，再一起合并 |
| 何时开启 | 只在 `ask` 里默认开启。Agent 自己发出的查询已经是术语，`retrieve` 默认不改写，可以用参数打开 |
| 降级 | 改写失败或超时（超过 3 秒）时直接用原句检索 |

### 评估

| | |
|---|---|
| 优点 | 对小王式口语提升最大；小块检索准，大块返回上下文完整，回答质量更好 |
| 缺点 | 每次 `ask` 多一次大模型调用，增加 1 到 3 秒；改写可能跑偏（比如把"VLAN"改成别的概念）；两层切块的索引更复杂 |
| 新增资源 | 和方案一相同，不再增加模型 |
| 工作量 | 方案一加 3 到 4 小时 |
| 风险 | 中：改写质量依赖模型，4B 模型上需要单独测 |

## 6. 对比和建议

| | 方案一：混合检索 | 方案二：+ 重排序 | 方案三：+ 改写 + 小块检索 |
|---|---|---|---|
| 命令和接口名查询 | 好 | 好 | 好 |
| 口语查询 | 较好 | 较好 | **最好** |
| 前 3 名准确率 | 较好 | **最好** | 较好 |
| 拒答稳定性 | 一般 | **最好** | 一般 |
| `retrieve` 增加的耗时 | 约 0.1 秒 | 约 0.3 到 1 秒 | 约 0.1 秒（`ask` 另加 1 到 3 秒） |
| 新增模型 | 1 个 | 2 个 | 1 个 |
| 8GB 机器 | 可以 | 紧张 | 可以 |
| llama.cpp 零安装版 | 降级为 BM25 | 降级为 BM25 | 降级为 BM25 |
| 工作量（在测试集之外） | 3 到 4 小时 | 5 到 7 小时 | 6 到 8 小时 |

**建议**：以**方案一为主线**，另外两个方案做成**可选增强**，用测试集数据决定开不开：

1. 测试集 → 测出基线（只用 BM25）
2. 改进解析和切块 → 回测
3. 方案一：向量检索 + RRF + 拒答阈值 → 回测（**到这一步就可以交付**）
4. 速度优化（2.6）→ 回测
5. 有时间再做：口语题还差 → 加方案三的问句改写；拒答或前 3 名不稳 → 加方案二的重排序
